# P3 Web Base Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Deliver the Vue CLI 5 front-end foundation: dependencies, authentication state, menu-driven routing guard, login entry, and button permission control.

**Architecture:** Vue 3 is bootstrapped with Pinia, Vue Router, and Element Plus. The user store persists only the two tokens; authenticated user data is refreshed from `GET /api/auth/userinfo`, then the permission store converts its `menus` tree into lazy-loaded views and the guard mounts these routes under the shell route.

**Tech Stack:** Vue CLI 5 / webpack, Vue 3, Vue Router 4, Pinia, Element Plus, Axios, and a Vue 3-native front-end slider verification interaction.

## Global Constraints

- Retain Vue CLI 5 and webpack; do not migrate to Vite.
- Use `/api` with Vue CLI proxy target `http://localhost:5169`.
- Send `userName` and `password` to `POST /api/auth/login`; `GET /api/auth/userinfo` returns camel-cased `userId`, `roles`, `perms`, and `menus`.
- Menu type `3` is a button and must never become a route.
- Route addition must end the first navigation with `{ ...to, replace: true }`.
- The slider must set `verified` before a login request can be sent; this is a front-end entry check, not a replacement for server-side login throttling.

- [x] **Step 1: Create static route tests through lintable, deterministic configuration**

Define named `Root`, `Login`, `NotFound`, and `Dashboard` routes. The 404 catch-all must be registered after the shell and must redirect to `/404`.

- [x] **Step 2: Implement layout, router, and guard**

The guard has three states: anonymous users can only enter `/login`; authenticated users are redirected away from `/login`; authenticated users with unloaded routes call `getInfo`, mount every generated route under `Root` using `router.addRoute('Root', route)`, flag success, and re-enter using `{ ...to, replace: true }`. On `getInfo` failure, clear user and permission state and redirect to `/login?redirect=<encoded destination>`. Set document title after each navigation.

- [x] **Step 3: Implement permission directive and login form**

Remove elements whose permission requirement is absent from `userStore.perms`; accept one permission string or an array requiring any match. The Element Plus form enforces user name plus a 6–64 character password, blocks submit before slider success, calls `authApi.login`, saves its `accessToken`/`refreshToken`, resets permission routes, and navigates to the safe redirect or `/`.
